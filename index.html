新手開發者必學

基礎技術決策知識

對於開發一個新專案來說，規劃層回答「這個系統解決什麼問題、不做什麼」，程式層回答「產品與功能落實的語法」

但在兩者之間的先備知識（此處稱之「技術決策 (Technical Decision)」）決定資料該長什麼形狀、東西會怎麼壞、金鑰放在哪裡、排程為什麼跑在錯的時刻。它不要求你能親手寫出實作，但要求你能判斷、能決定、能在壞掉時定位。

這份講義將基礎知識拆解成 L1~L9，每塊講四到六個核心觀念。每個觀念都白話說明機制、給一個能自己驗證的例子、再說明它如何改變你的做法。

怎麼讀。一次讀一層就好。「要學什麼」是那一層的題目清單，「核心觀念」是可以直接吸收的部分——讀完就知道了，不必再去別處查。

術語都附英文。因為延伸學習幾乎只能靠英文關鍵字搜到有用的東西。括號裡的英文可以直接拿去查。

層號是位置，不是難度。編號標示的是「這件事發生在系統的哪個位置」，從最底層的執行環境到最上層的觀測。

L1

執行環境與命令列

一個指令跑起來時，實際發生了什麼。

為什麼學

其他八層的錯誤訊息，全部要經過這一層才讀得懂。缺了它，你會把「環境沒對」誤判成「程式有錯」，然後花好幾個小時修一段本來沒問題的程式碼。

它也是唯一能解釋這三種常見困境的一層：套件明明裝了卻找不到、日誌裡什麼都沒有、服務說啟動成功但外面連不到。

要學什麼

  • 搜尋路徑——同名指令跑到哪一個 PATH resolution
  • 程序的環境——環境變數怎麼傳、傳給誰 process environment
  • 結束碼與訊號——程式最後說的那句話 exit code, signal
  • 兩條輸出管線與緩衝——為什麼日誌會消失 stdout/stderr, buffering
  • 綁定位址與端口——誰連得到你 bind address, port

核心觀念

1搜尋路徑：為什麼「裝了卻找不到」

你在終端機打 python3 時，系統並不知道你指的是哪一個檔案。它拿環境變數 PATH 裡列的目錄，從左到右一個個找，第一個找到的就用，找到就不再往下看。

虛擬環境（virtual environment）的全部魔法就是這件事：它把自己的目錄插到 PATH 最前面。所以「啟用虛擬環境」不是什麼複雜機制，只是改了搜尋順序。

例 
$ echo $PATH
/Users/me/.venv/bin:/usr/local/bin:/usr/bin:/bin

$ command -v python3
/Users/me/.venv/bin/python3      ← 命中的是這個

$ /usr/bin/python3 -c "import openpyxl"   ← 這個裝了
$ python3 -c "import openpyxl"            ← 這個沒裝 → ModuleNotFoundError

同一台機器、同一個指令名稱、兩個不同的程式。「套件沒裝」這個訊息是真的——只是它講的是另一個 Python。

所以看到「找不到模組」時，第一個動作是 command -v python3（或在 Python 裡印 sys.executable），確認你問的是哪一個。先確認位置，再決定要不要安裝。

2環境變數是每個程序自己的一份影本

環境變數不是全域設定。程序啟動的那一刻，系統給它一份影本；它之後生的子程序再繼承一份影本。所以：你在終端機 export 的東西，只影響之後從這個終端機啟動的程序，對已經在跑的程序完全沒有影響，對別的終端機也沒有影響。

這解釋了一個常見的困惑：「我明明設了那個變數。」你設在你的終端機那一份裡；服務被平台啟動時拿到的是平台給的另一份。兩份毫無關係。

例

同一個變數有四份互不相干的來源，缺哪一份就在哪一層失效：

來源誰看得到
export FOO=1這個終端機之後啟動的程序
.env 檔只有主動去讀它的程式（系統本身不認識這個檔）
平台的服務變數平台啟動的那個服務
排程／容器的設定那個任務的那一次執行

.env 這一列特別容易誤解：作業系統完全不知道有這個檔案，是你的程式用套件去讀它、再塞進自己的環境裡。所以在別的執行方式下它可能根本沒被讀到。

所以「變數沒生效」要問的是「這一份是誰給的」，不是「我是不是打錯了」。

3結束碼：程式最後說的那句話

程序結束時會留下一個 0 到 255 的數字。0 代表成功，非 0 代表失敗——這是唯一一句所有工具都聽得懂的話。自動重啟策略、排程器的成敗判斷、&& 要不要接著跑，全都只讀這個數字。

如果程序是被訊號（signal）殺掉的，結束碼是 128 + 訊號編號。這幾個數字沒有道理可推，只能認得：

例
碼意思通常代表
0正常結束成功
1一般錯誤程式自己回報失敗
130128+2 中斷你按了 Ctrl-C
137128+9 強制終止記憶體用盡被系統殺掉
139128+11 記憶體區段錯誤原生程式碼崩潰
143128+15 終止請求平台要它關機（部署、縮容）
 
$ ./my_script.sh
$ echo $?          ← 讀上一個指令的結束碼
137                ← 不是程式邏輯錯，是記憶體不夠

所以看到 137 不要去讀程式碼，去看記憶體上限；看到 139 往原生擴充套件那邊想。而如果你的程式把錯誤攔下來、印一行訊息、然後正常結束——它的結束碼是 0，平台會認為它成功了，重啟策略不會救它。

4兩條輸出管線，以及日誌為什麼會消失

程序有兩條獨立的輸出管線：標準輸出（stdout，正常結果）和標準錯誤（stderr，錯誤訊息）。> 只導走前者，所以「我把輸出存到檔案了但錯誤訊息不在裡面」是正常行為，要 2>&1 才會併進去。

更常咬人的是緩衝（buffering）。輸出接到終端機時是「寫一行就送出一行」；但接到管線或檔案時（也就是所有部署環境），系統會改成攢滿幾千位元組才送一次。後果是：日誌延遲很久才出現，而程式崩潰時還沒送出的那一批直接消失——你會看到一個沒有任何線索的當機。

例 
# 崩潰前的日誌不見了，因為還在緩衝區裡
python worker.py > out.log

# 關掉緩衝，每一行立刻送出
python -u worker.py > out.log
# 或設環境變數（容器裡的標準做法）
PYTHONUNBUFFERED=1

所以任何跑在容器或排程裡的程式，都要關掉輸出緩衝。「崩潰前完全沒有日誌」這個症狀，八成不是程式沒印，是印了但沒送出去。

5綁定位址：0.0.0.0 與 127.0.0.1 的差別

一台機器有多張網路介面（network interface）。其中一張叫迴環（loopback），位址是 127.0.0.1，它的流量永遠不離開這台機器。

服務啟動時要選擇「聽哪一張」。綁 127.0.0.1 表示只接受本機的連線；綁 0.0.0.0 表示所有介面都聽。兩者都會讓服務正常啟動、日誌顯示成功——差別只在外面連不連得到。

例

容器有自己的一組網路介面，包含自己的迴環。所以容器裡綁 127.0.0.1 意思是「只有這個容器裡面連得到」，即使你把端口正確映射出來也一樣連不到。

# 本機開發沒問題，部署後連不到
app.run(host="127.0.0.1", port=8000)

# 容器 / 雲端的正確寫法
app.run(host="0.0.0.0", port=int(os.environ["PORT"]))

所以「啟動成功但連不到」先看兩件事：綁定位址是不是 0.0.0.0，端口是不是用平台注入的那一個。這兩個錯誤都不會產生任何錯誤訊息。

L2

版控的資料模型

你的檔案在時間軸上的狀態，以及誰拿得到什麼。

為什麼學

大部分人會用五、六個版控指令，但不知道它們在動什麼。結果是：出狀況時不敢動手，因為不知道哪個操作會弄丟東西；以及一個更嚴重的後果——把秘密提交進去之後，用錯誤的方式「刪掉」它，以為安全了。

這一層需要的知識量最少，但誤解的代價最高。

要學什麼

  • 它到底存了什麼——內容尋址的快照 content-addressed objects
  • 分支與 HEAD——為什麼分支很便宜 ref, pointer
  • 三個區域——工作區、索引、提交 working tree, index, HEAD
  • 忽略清單的作用範圍——它管不到什麼 gitignore, tracked files
  • 歷史的不可變性——與秘密輪替 immutability, secret rotation

核心觀念

1Git 存的是完整快照，用內容當名字

直覺會以為版控存的是「每次改了哪幾行」。實際上它存的是完整快照：每次提交都記錄「這一刻所有檔案長什麼樣」。差異是顯示時才算出來的。

而每個物件的名字，是它內容的雜湊值（hash）。兩個內容一樣的檔案，會是同一個物件，只存一份——這是為什麼存完整快照不會爆掉。

例

三種物件就構成整個系統：

物件內容
blob一個檔案的內容（不含檔名）
tree一個目錄：檔名 → blob 或 tree 的對應
commit一個 tree ＋ 上一個 commit ＋ 作者、時間、訊息

提交的雜湊值涵蓋了「內容＋上一個提交」。所以改動任何一個舊提交，它之後的每一個提交的名字都會變——歷史在結構上就無法被就地修改。

所以「修改歷史」實際上是「重建一條新歷史」。任何人手上的舊複本、任何備份、任何分支，都還帶著原本那一份。

2分支只是一個裝著雜湊值的檔案

分支（branch）不是一份程式碼的複本。它是一個小檔案，裡面只有一個提交的雜湊值。HEAD 則是另一個指標，指向「你現在在哪個分支上」。

這解釋了兩件事：為什麼開分支、切分支幾乎不花時間（只是改一個指標）；以及為什麼刪掉分支不等於刪掉提交——那些提交還在，只是沒有指標指著它們，所以你找不到。

例 
.git/refs/heads/main   ← 檔案內容就一行雜湊值
.git/HEAD              ← 內容：ref: refs/heads/main

「提交之後才發現弄錯了」通常救得回來，因為那個提交物件還在，只要找到它的雜湊值就能把指標指回去（git reflog 記著你最近去過哪些地方）。

所以版控裡最難救回來的，不是「提交錯了」，而是從來沒提交過的東西——它不是任何物件，只是硬碟上的檔案。

3三個區域，兩次搬運

同一份檔案，在三個地方各有一份狀態：工作區（你正在編輯的）、索引（index／暫存區，下次要提交的內容）、最近一次提交。add 把工作區搬到索引，commit 把索引變成新提交。

知道這件事最直接的好處，是看得懂狀態輸出的兩欄——很多人以為那些字母是隨機的：

例 
$ git status --short
M  db.py        ← 左欄有字：已加入索引，會被提交
 M app.py       ← 右欄有字：改了但沒加入，不會被提交
MM notify.py    ← 兩欄都有：加入了，之後又改了（提交的是加入時那版）
?? alerts.py    ← 完全沒被追蹤過

左欄＝索引與提交的差異，右欄＝工作區與索引的差異。MM 那一行是最容易出錯的情況：你以為提交的是現在看到的版本，其實是你 add 那一刻的版本。

所以提交前掃一眼狀態輸出的右欄。右欄有字的檔案，是你以為會進去、但不會進去的東西。

4秘密一旦進了歷史，就只能輪替

忽略清單（.gitignore）只對「從未被追蹤過」的檔案有效。一個檔案只要被提交過一次，它就進入追蹤狀態，之後把它加進忽略清單完全沒有作用——它會繼續被追蹤，而且歷史裡那一份永遠都在。

就算你用改寫歷史的工具把它從所有提交裡挖掉，也只是在你這一份倉庫成立。任何已經取得過的複本、任何分支、任何備份、任何自動掃描服務的紀錄裡，那個值都還在。

例

正確的處置順序，第一步和最後一步不能顛倒：

1. 先輪替那個秘密        ← 讓歷史裡那一份失效，這是唯一真正有效的動作
2. 停止追蹤該檔案        git rm --cached .env
3. 加進忽略清單          echo ".env" >> .gitignore
4. （選擇性）改寫歷史    只是清理，不是修補

所以發現秘密進了版控，第一個動作是去把那把金鑰換掉，不是去研究怎麼刪檔案。刪檔案不會讓已經洩漏的憑證失效。

L3

依賴與環境重現

程式跑起來時，它身邊有哪些別人寫的東西。

為什麼學

這一層負責解答「本機正常、部署失敗」這一整類問題。缺了它，你會反覆去改一段其實沒問題的程式，而真正的差異在兩邊裝出來的東西不一樣。

它也解釋了一個特別惡劣的現象：首頁完全正常，但某個功能一按就掛掉——而且只在部署後發生。

要學什麼

  • 模組怎麼被找到——搜尋順序 sys.path, module resolution
  • 三種相依身分——直接、間接、選用 direct, transitive, optional
  • 延遲載入——為什麼錯誤會晚到 lazy import
  • 宣告與鎖定——版本語意與可重現 semver, lock file
  • 預編譯與原生擴充——無訊息崩潰的來源 wheel, C extension

核心觀念

1模組的搜尋順序，和指令一樣是「第一個命中的贏」

Python 執行 import requests 時，會按 sys.path 這個清單的順序找，第一個找到的就用。清單的順序大致是：腳本所在目錄 → PYTHONPATH 指定的目錄 → 這個解譯器自己的套件目錄。

注意最後一項：套件目錄是綁在解譯器身上的，不是綁在專案身上。所以「哪個 Python」決定了「哪一套套件」——這就是虛擬環境的原理，它有自己的解譯器與自己的套件目錄。

例

診斷「明明裝了卻找不到」，兩行就夠：

$ python3 -c "import sys; print(sys.executable)"
/Users/me/.venv/bin/python3        ← 現在用的是這個解譯器

$ python3 -c "import sys; print(*sys.path, sep='\n')"
/Users/me/proj                    ← 腳本目錄（第一優先，會蓋掉同名套件）
/Users/me/.venv/lib/python3.11/site-packages   ← 套件在這裡找

第一項還帶來一個陷阱：如果你的檔案叫 requests.py，import requests 會匯入你自己那個檔案，而不是套件——而錯誤訊息會是某個看起來毫無關係的屬性不存在。

所以先印 sys.executable，再考慮安裝。以及不要把自己的檔案取成跟套件一樣的名字。

2三種相依身分，第三種是部署地雷

直接相依是你在程式裡明確引入的。間接相依（transitive）是那些套件自己需要的東西——你不會列它，但它會被一起裝上。

選用相依（optional dependency）是第三種，也是麻煩的來源：某個套件只在你用到它的某個特定功能時才需要另一個套件，而它沒有把那個套件列為硬性需求。安裝時一切正常、啟動時一切正常，只有走到那條路徑才炸。

例

為什麼它只在特定路徑炸？因為引入語句寫在函式裡面，而不是檔案開頭——這叫延遲載入（lazy import）：

# 某個套件內部的寫法
def start_login_flow():
    import httpx            ← 執行到這一行才去找它
    ...

# 於是：
#   安裝    → 成功（沒人檢查 httpx）
#   啟動    → 成功（沒執行到這個函式）
#   首頁    → 成功
#   點登入  → 500，ImportError

所以「部署後某個功能才壞」要先懷疑選用相依，而不是懷疑那個功能的邏輯。也因此：驗證部署不能只開首頁，要把每一條路徑實際走一次——沒被走過的路徑等於沒被驗證。

3宣告檔說「我要什麼」，鎖定檔說「實際裝了什麼」

版本號通常是三段：主版本．次版本．修補（major.minor.patch）。約定是——修補只修錯誤，次版本加功能但不破壞既有用法，主版本可以破壞。這個約定叫語意化版本（semantic versioning），是慣例而非保證。

所以 >=2.0 這種寫法意思是「2.0 以上都行，包含未來的 3.0」——它換到自動修補，代價是同一份宣告在不同時間會裝出不同的東西。三個月後重建環境，行為可能就變了，而你的宣告檔一個字都沒改。

例
檔案記錄什麼用途
requirements.txt我要求的（可能是範圍）宣告意圖
requirements.lock
poetry.lock / uv.lock		實際解析出的完整清單，含所有間接相依的確切版本重現環境
 
# 想知道現在到底裝了什麼
$ pip freeze
# 兩邊行為不同時，比對的應該是這份輸出，不是宣告檔

所以「本機好、上線壞」的第一個動作是比對兩邊的 pip freeze。而如果你需要「三個月後還跑得出一樣的結果」，就要有鎖定檔，不能只有宣告檔。

4原生擴充：崩潰時沒有 Python 的錯誤訊息

有些套件的核心是用 C 寫的，安裝時直接下載預編譯好的檔案（叫輪子／wheel），而不是在你的機器上編譯。它們通常快得多。

代價是：C 那一層崩潰時，不會產生 Python 的錯誤堆疊。你看到的是程序直接消失、結束碼 139，什麼線索都沒有。常見的觸發條件是多執行緒環境——同一個套件單獨執行時很穩，放進多執行緒的服務裡就偶發性崩潰。

例

許多套件同時提供兩種版本，選擇是有理由的：

版本特性適合
原生擴充版快；可能與特殊執行環境衝突單獨執行的批次工作
純 Python 版慢一些；行為可預測多執行緒的常駐服務

同一個專案在兩處用同一功能的兩種版本，是正確設計，不是妥協。

所以「沒有錯誤訊息就死掉」不要繼續在 Python 程式碼裡找原因。往這個方向想：是不是有原生擴充，換成純 Python 版還會不會發生。

延伸學習方向

可以直接查的關鍵字
sys.path · module shadowing · transitive dependency · optional dependency · lazy import · semantic versioning · lock file · dependency pinning · python wheel · C extension GIL
值得讀的東西
Python 官方文件的 Modules → The Module Search Path 一節（很短，但把搜尋順序講死了）。以及你用的套件管理工具自己的「lock」章節——每個工具的鎖定機制不同，這裡不能靠通論。
動手方向
建一個乾淨環境，只裝宣告檔裡的東西，然後把程式的每一條主要路徑都實際走一次：登入、送出、匯出、下載。記下哪一條先炸——那就是宣告檔和執行期需求之間的落差。

L4

關聯資料庫的機制

資料該長什麼形狀，以及誰負責把錯的資料擋在門外。

為什麼學

這一層決定系統的形狀，而形狀是最貴的東西——程式錯了改一天，資料模型錯了改一個月，而且那段時間累積的資料可能已經不可信。

它也是唯一能防住這一類故障的一層：畫面完全正常，但數字是錯的。這種錯不會報錯、不會有例外、不會有任何跡象，只會在某天對帳時發現，然後你無法回推是哪一天開始錯的。

要學什麼

  • 事實、參數、推導值——什麼該存、什麼不該存 derived data
  • 約束——把規則交給資料庫 constraint, NOT NULL, UNIQUE, CHECK, FK
  • 空值的三值邏輯——NULL 不是 0 three-valued logic
  • 浮點與定點——金額為什麼不能用浮點 IEEE 754, NUMERIC
  • 交易與隔離——全有或全無 transaction, ACID, isolation level
  • 索引——為什麼快、什麼時候不管用 B-tree, leftmost prefix

核心觀念

1三分法：事實、參數、推導值

資料庫裡的每個欄位都屬於三類之一：

事實是發生過的事——一筆交易、一次點擊、一個公布的數字。它已經發生了，所以不該被修改。參數是你的設定——門檻、比例、開關。它會改，但每次改都該留下痕跡。推導值是從前兩者算出來的——平均、總和、報酬率、狀態。

關鍵規則是：推導值不要存。因為它會和來源不同步，而且不同步時沒有任何機制會通知你。

例

假設你把「平均成本」存成一個欄位。某天你補記一筆漏掉的早期交易：

交易表   ← 多了一筆（正確）
均價欄位 ← 沒有人去改它（錯了）
畫面     ← 顯示一個看起來很合理的數字（錯得很安靜）

之後所有依賴均價的數字全部錯，而系統一次錯誤訊息都不會給你。

合法的中間解有兩種，但兩種都是「明確宣告它是推導出來的」：視圖（view，每次查詢重算）；或產生欄位（generated column，由資料庫自己維護，你無法手動寫入）。真的需要為效能落地時，用物化視圖（materialized view）並排定重算，而不是手寫一個誰都能改的普通欄位。

所以拿到任何一張表，逐欄問「這是事實、參數，還是推導值」。看到推導值被存成普通欄位，就是找到一個未來的靜默錯誤。

2約束：讓錯誤在寫入的那一刻發生

約束（constraint）是你在建表時宣告的規則，資料庫會強制執行。它的價值不在「幫你檢查」——你自己也能在程式裡檢查。價值在於：它讓錯誤發生在寫入那一刻，而不是幾個月後在報表上。

而且它擋得住你想不到的路徑：批次匯入、修補腳本、別人直接連資料庫改。程式裡的檢查只保護程式這一條路。

例
約束擋住什麼不設會發生的事
NOT NULL這個欄位不能沒有值時間戳為空的那筆資料，讓「最新的一筆」永遠停在某一刻且不報錯
UNIQUE這個值不能重複同一件事被記兩次，統計全部翻倍
CHECK值必須符合條件負數的股數、超過 100 的百分比安靜存進去
FOREIGN KEY必須對應到另一張表存在的列指向不存在標的的孤兒資料，JOIN 時整批消失
PRIMARY KEY身分：唯一且不為空無法指定「就是這一列」

唯一鍵還有一個額外用途：它是「重跑不會寫兩筆」的實作基礎——沒有唯一鍵，就沒有辦法讓寫入變成可安全重複的操作。

所以建表時的判斷句是：這條規則會不會有人忘記？會，就交給資料庫。約束擋下來的那一刻，是這筆錯誤唯一會發出聲音的時刻。

3NULL 不是 0，也不是「否」，是「不知道」

這是整層裡最容易誤解、後果最嚴重的一個觀念。空值（NULL）不是一個值，它是「這裡沒有資訊」。所以任何和它做的運算，結果都是「不知道」。

於是布林判斷不是兩種結果，而是三種：真、假、不知道。而條件篩選只留下「真」——「不知道」和「假」一樣會被丟掉。

例

真值表，兩行就能解釋大量詭異行為：

運算結果後果
TRUE AND NULLNULL條件不成立，這一列被丟掉
FALSE AND NULLFALSE（這個沒問題）
TRUE OR NULLTRUE（這個也沒問題）
NULL = NULLNULL永遠不成立——要用 IS NULL
x <> 'A'NULLx 為空時，這一列不會出現在「不等於 A」的結果裡
 
-- 一個守門查詢
SELECT * FROM state WHERE enabled AND heartbeat > now() - interval '60 s';

-- heartbeat 是 NULL 時：TRUE AND NULL → NULL → 這列被丟掉 → 回傳零列
-- 如果程式把「零列」當成「不該執行」，這個任務就永久停擺，而且不報錯

-- 明確處理空值，並宣告「查不到時算什麼」
SELECT COALESCE(
         (SELECT enabled AND heartbeat > now() - interval '60 s'
            FROM state WHERE id = 1),
         TRUE            -- 查不到 → 照跑
       ) AS should_run;

另外兩個實用差別：聚合函式會跳過空值（所以 AVG 的分母可能不是你想的那個數）；COUNT(*) 數列數，COUNT(欄位) 只數該欄非空的列。

所以任何依賴布林判斷的守門機制，都要明確處理「不知道」的情況，並且明確宣告查不到資料時算什麼。沒宣告的話，它會壞向實作細節碰巧決定的那一邊。

4浮點數存不了小數：金額為什麼要用定點

浮點數（float / double）用二進位科學記號存數字。問題是：很多十進位小數在二進位裡是無限循環的，就像 1/3 在十進位是 0.333⋯ 一樣。0.1 就是其中一個——它存進去的其實是一個非常接近但不等於 0.1 的值。

單次運算誤差小到看不見，但累加會讓誤差浮上來。而金額的累加正是這種操作，於是你得到一個無法解釋的尾差，而且是對帳時最難查的那一類。

例 
$ python3 -c "print(0.1 + 0.2)"
0.30000000000000004          ← 不是 0.3

$ python3 -c "print(f'{0.1:.20f}')"
0.10000000000000000555       ← 存進去的其實是這個

$ python3 -c "print(0.1 + 0.2 == 0.3)"
False

定點型別（NUMERIC / DECIMAL）改成以十進位位數儲存，所以它存得下精確的 0.1。代價是運算慢一些——對金額來說完全值得。

資料該用
金額、股數、比例NUMERIC(精度, 小數位)
測量值、統計中間值DOUBLE PRECISION（誤差可接受）
需要極致效能的金額整數存最小單位（例如以「分」為單位）

所以金額欄位一律定點型別。而且要注意跨邊界時的降級——資料在資料庫裡是定點，經過某些驅動或轉成另一種語言的型別時可能變成浮點，於是尾差在系統邊界上悄悄產生。要在邊界明確轉換。

5交易：全部發生，或全部沒發生

交易（transaction）是把好幾個操作包成一個不可分割的單位。中間任何一步失敗，整批退回，資料庫回到開始前的樣子。

常被引用的四個性質叫 ACID：原子性（全有或全無）、一致性（不會違反約束）、隔離性（其他人看不到你做一半的狀態）、持久性（提交後就算斷電也還在）。

其中隔離性有個實務細節：它有等級。多數資料庫預設的等級只保證「你不會讀到別人未提交的資料」，但不保證你在同一個交易裡讀兩次會得到同樣的結果。這是「先讀出來、算一算、再寫回去」這種寫法會出錯的原因。

例

交易還有一個很少被提到的用途——最乾淨的測試隔離：

BEGIN;
  -- 寫入你需要的測試資料
  -- 執行要驗證的計算
  -- 比對結果
ROLLBACK;      ← 資料庫回到原狀，什麼都沒留下

好處是你用的是真實的結構與真實的約束，而不是一份可能已經和正式環境不同步的複本。不需要另外維護一套測試資料庫。

所以凡是「這幾件事必須一起成立」的地方就開交易。而「先讀、再算、再寫」的模式要改成一步完成的條件更新（例如 UPDATE ... WHERE 版本 = 讀到的版本），否則兩個同時執行的人會互相覆蓋。

6索引是一本排好序的目錄

沒有索引，資料庫要找一列資料只能從頭掃到尾。索引（index）是額外維護的一份排序結構（最常見的是 B-tree），像書末的索引一樣，讓它能直接跳到位置，而不是逐頁翻。

代價有兩個：占空間，以及每次寫入都要順便更新索引，所以寫入變慢。這就是「不要每個欄位都建索引」的原因——索引要跟著你實際會下的查詢建。

例

複合索引有個必須知道的規則：只能從最左邊開始用（leftmost prefix）。假設索引建在 (symbol, trade_date)：

查詢條件用得到嗎
WHERE symbol = '2330'✓ 用得到
WHERE symbol = '2330' AND trade_date > …✓ 最理想
WHERE trade_date > …✗ 用不到（跳過了最左邊那欄）

想知道某個查詢實際上有沒有用到索引，不要猜——資料庫可以直接告訴你：

EXPLAIN ANALYZE SELECT ... ;
-- 輸出裡出現 Seq Scan（全表掃描）＝ 沒用到索引
-- 出現 Index Scan ＝ 用到了

所以小規模系統通常只需要極少數索引，力氣花在「不讓錯資料進來」比花在「讓查詢變快」值得。等到真的慢了，用 EXPLAIN 看實際執行計畫再決定，不要憑感覺加索引。

L5

資料源與網路協定

你的系統和外面世界之間的每一次對話。

為什麼學

實際故障數量最多的一層。因為外面的世界不受你控制：它會改版、會限流、會回一個格式正確但內容是空的東西、會在你最需要它的時候不回應。

而這些狀況大多不會觸發你寫的錯誤處理，因為它們在技術上都算「成功」。

要學什麼

  • 一次呼叫的四段——各自的失敗方式 DNS, TCP, TLS, HTTP
  • 狀態碼的語意——它講傳輸不講內容 status code semantics
  • 逾時的兩個數字——連線與讀取 connect / read timeout
  • 重試與幂等——什麼可以重試 backoff, idempotency key
  • 位元組與文字——編碼與亂碼 encoding, UTF-8
  • JSON 的兩個坑——日期與大整數 JSON number precision

核心觀念

1一次呼叫其實是四段，各有各的失敗

你寫一行「去抓這個網址」，實際上發生了四件事，順序固定，每一段都可能單獨失敗——而且失敗訊息長得完全不一樣：

例
段做什麼失敗時你會看到
DNS網域名 → IP 位址找不到主機（name resolution failed）
TCP和那個 IP 建立連線連線被拒絕、連線逾時
TLS加密協商、驗證對方憑證憑證錯誤、憑證過期、協定版本不合
HTTP送出請求、拿回回應狀態碼 4xx / 5xx、內容解析失敗

知道分段的實用價值是：「連不上」和「連上了但回錯」要往完全不同的方向查。前者是網路與位址問題，後者是應用與參數問題。

所以看到錯誤訊息先歸段。名稱解析失敗不必去檢查你的權杖對不對；憑證錯誤不必去檢查參數格式。

2狀態碼講的是傳輸，不是內容

HTTP 狀態碼（status code）分四類：2xx 成功、3xx 重導、4xx 你的請求有問題、5xx 對方出問題。

關鍵在於 200 的真正含義是「我收到了、我處理了、我把回應送出去了」。它完全沒有保證內容是對的、是完整的、甚至不保證裡面有東西。「參數錯誤導致查不到資料」在很多服務上是 200 加一個空結果，不是 400。

例 
回應狀態：200 OK
回應內容：{"data": [], "rtcode": "0000"}

# 三件事都成立：連線成功、狀態正常、格式正確
# 但資料是空的，而你的程式如果照常寫入 → 一批合法的空值進資料庫

這種「安靜地成功」通常來自參數錯誤：代號的前綴錯了、日期格式對方不認、權杖只有部分權限。對方沒有義務告訴你。

所以每個對外呼叫都要對內容本身做健全性檢查：該有的欄位在不在、數量是否合理、關鍵值是否為空。檢查不過就拒絕寫入並發出聲音——寧可在寫入時失敗得大聲，也不要在讀取時錯得安靜。

3逾時是兩個數字，而預設值通常是「無限等」

逾時（timeout）不是一個數字，是兩個：連線逾時（等對方接受連線）和讀取逾時（連上了，等對方把資料送完）。兩者的合理值差很多——連線幾秒就該放棄，讀取可能要給幾十秒。

而多數 HTTP 客戶端預設不設逾時，也就是無限等待。這是一個很容易忽略的預設值，後果卻很嚴重：對方掛住時，你的流程一起掛住，而且沒有錯誤訊息——從外面看就像還在執行。

例 
# 最壞的一種：發送告警的呼叫沒有逾時
requests.post(webhook, json=payload)
# 對方掛掉時 → 你的主流程卡在這裡
# → 告警機制本身變成故障源，而且正好發生在你最需要收到告警的時候

# 兩個數字分開設
requests.post(webhook, json=payload, timeout=(3, 10))
#                                            ↑連線 ↑讀取

所以每一個對外呼叫都要有逾時，一個例外都不要留。尤其是通知與告警那幾條——它們最容易被忘記，而它們失效的時機最糟。

4重試：只重試該重試的，而且要能安全重試

錯誤分兩種。暫時性的（連線中斷、429 被限流、5xx 對方內部錯誤）值得重試。永久性的（400 參數錯、401 認證失敗、404 不存在）重試一百次結果都一樣，只是浪費。

重試的間隔要用指數退避加抖動（exponential backoff with jitter）：1 秒、2 秒、4 秒、8 秒，每次再加一點隨機偏移。指數是為了不在對方最脆弱的時候持續加壓；抖動是為了避免所有客戶端同時重試，把對方再壓垮一次。

例

還有一個關鍵問題：這個操作重試安全嗎？HTTP 方法本身就有答案：

方法重複執行重試
GET結果相同安全
PUT / DELETE結果相同（設計上）安全
POST會再建立一次不安全

「結果相同」這個性質叫幂等（idempotent）。要讓 POST 變成可安全重試，做法是帶一把幂等鍵（idempotency key）——你自己產生一個唯一字串，對方看到同一把鍵就不再重複建立。付款類的服務幾乎都支援這個。

所以寫重試邏輯前先問兩題：這個錯誤重試有用嗎？這個操作重試安全嗎？兩題都是「是」才重試。而網路超時最麻煩——你不知道對方到底做了沒有，這時幂等鍵是唯一的解法。

5位元組與文字：亂碼是怎麼來的

檔案與網路上流動的都是位元組，不是文字。要變成文字，必須知道用哪一套編碼（encoding）去解讀。用錯的那一套去解，就是亂碼——而且過程完全不會報錯，只是解出一堆看不懂的字。

現在的標準是 UTF-8，但舊系統（尤其是政府與傳統企業的匯出檔）常常是舊編碼。而檔名比內容更容易出錯：壓縮檔格式裡有一個旗標位元專門標示「檔名是 UTF-8」，舊工具不設這個旗標，於是檔名的編碼變成不確定的。

例 
# 錯的解法：靠檔名找檔案
for name in zipfile.namelist():
    if "景氣" in name:        ← 檔名編碼一變，這裡就永遠找不到
        ...

# 對的解法：靠內容特徵找檔案
for name in zipfile.namelist():
    head = zf.read(name)[:200].decode("utf-8", errors="replace")
    if head.startswith("Date") and "綜合分數" in head:
        ...

而「找不到」如果被實作成安靜跳過，那一次的資料就永久缺了。

所以判斷「這是哪一個檔案」時，用內容特徵而不是檔名。而任何解碼失敗都要出聲，不要用「忽略錯誤」把它蓋掉。

6JSON 的兩個坑：沒有日期，數字是浮點

JSON 的型別只有六種：物件、陣列、字串、數字、布林、空值。沒有日期型別——所有日期都是字串，格式全靠雙方約定。所以「時區到哪去了」這類問題在 JSON 邊界特別常發生：一個沒有時區標記的時間字串，接收端只能猜。

第二個坑更隱蔽：JSON 的數字在多數實作裡是雙精度浮點。所以超過 253 的整數（大約 9,007,199,254,740,992）會失去精度。這對長整數識別碼是致命的——雪花演算法產生的 ID、某些系統的訂單號都在這個範圍。

例 
$ python3 -c "import json; print(json.loads('{\"id\": 9007199254740993}'))"
{'id': 9007199254740993}      ← Python 沒事（它有大整數）

# 但同一份 JSON 進到 JavaScript：
JSON.parse('{"id": 9007199254740993}')
// { id: 9007199254740992 }   ← 最後一位變了，而且不報錯

兩個坑的解法是同一個：把它們變成字串。時間用帶時區的標準格式字串（2026-09-09T13:30:00+08:00），長識別碼用字串傳。

所以設計介面時，時間一律帶時區的字串，識別碼一律字串。這兩件事後來要改都很痛，因為兩邊都已經依賴既有格式。

L6

程序、排程與並發

什麼時候發生、發生幾次、同時發生會怎樣。

為什麼學

這一層的故障有個共同特徵：在測試時不會發生。因為測試是一次一件事，而問題只在兩件事剛好同時發生時出現——可能一個月一次，而且無法重現。

它也負責時間。而時間的錯誤特別安靜：排程照跑，只是跑在錯的時刻，所有「有沒有執行」的檢查都會顯示正常。

要學什麼

  • 程序與執行緒——共享記憶體才有競態 process, thread
  • 檢查與動作之間的空隙——競態的本質 race condition, TOCTOU
  • 原子操作——把兩步合成一步 atomic, compare-and-swap
  • 租約與心跳——鎖被帶走怎麼辦 lease, TTL, heartbeat
  • 排程與時區——表達式不帶時區 cron, UTC, DST
  • 交付語意——至少一次與幂等 at-least-once delivery

核心觀念

1程序與執行緒：問題出在共享的東西

程序（process）有自己獨立的記憶體，兩個程序看不到對方的變數。執行緒（thread）是同一個程序裡的多條執行流，共享同一份記憶體。

這個差別決定了問題會出在哪：凡是共享的東西，就是競態的發生地。同一個程序裡的變數、多個程序共享的一張資料庫表、多台機器共用的一個檔案——都是共享，都會出同一類問題。

例

順帶釐清兩個常被混用的詞：並發（concurrency）是多件事交錯進行，即使只有一個處理器也成立；並行（parallelism）是真的同時執行，需要多個處理器。

實務上這個區分不太重要，因為兩者都會產生競態——只要「A 做到一半、B 插進來」就足夠了，不需要真的同時。

所以盤點風險時，找的是「有幾個東西在寫同一個地方」。答案大於一，就要往下一個觀念想。

2檢查與動作之間的空隙

幾乎所有並發錯誤都是同一個形狀：你先檢查一個條件，然後根據檢查結果去動作，而在這兩步之間，世界變了。這個模式有個名字叫「檢查到使用之間」（TOCTOU, time-of-check to time-of-use）。

它的危險在於程式碼看起來完全正確——你確實檢查了。

例 
時間  執行者 A                    執行者 B
────  ────────────────────────  ────────────────────────
 t0   查詢：有人在跑嗎？→ 沒有
 t1                             查詢：有人在跑嗎？→ 沒有
 t2   標記「我在跑」
 t3                             標記「我在跑」
 t4   抓資料 → 寫入
 t5                             抓到較舊的資料 → 寫入
                                ↑ 覆蓋了 A 的新資料，畫面上的值退步了

加鎖能縮小空隙，但不能消滅它——因為「取得鎖」本身也是一次檢查加一次動作，除非那個動作在底層是不可分割的。

所以看到「先查再寫」的程式碼，就要假設中間會被插隊。這不是罕見情況，是預設情況。

3解法是原子操作：把兩步合成一步

真正的解法不是把空隙變小，而是讓檢查和動作變成一個不可分割的操作（atomic operation）。做法有幾種，都是把條件放進寫入語句本身：

例
手法怎麼做擋住什麼
唯一約束讓資料庫拒絕重複的鍵同一件事被記兩次
條件更新UPDATE … WHERE 版本 = 我讀到的版本，影響 0 列就代表被人搶先了兩人互相覆蓋（lost update）
時序守衛UPDATE … WHERE 新時戳 >= 現有時戳舊資料覆蓋新資料
寫入時衝突處理INSERT … ON CONFLICT DO UPDATE（upsert）「先查有沒有、再決定插入或更新」的空隙

共同點是：條件的判定發生在資料庫內部，和寫入是同一個動作，中間沒有你的程式可以被插隊的位置。

另外有個實務細節值得記：時序守衛用 >= 還是 > 會決定「同一個時戳的資料寫不寫得進去」。用 > 的話，同時戳的更新會被靜默丟棄。

所以並發問題的正解幾乎都在資料層，不在程式層。兩道防線的分工是：旗標或鎖讓它們盡量不要同時發生，原子操作讓同時發生也無害。第二道不能省。

4鎖會被帶走：改用有期限的租約

鎖有個致命問題：持有者崩潰時，鎖不會自己釋放。程序被殺掉、機器斷電、使用者直接關掉瀏覽器——這些都不會通知任何人，於是那把鎖永遠卡在那裡，而被它擋住的工作永久停擺。

解法是租約（lease）：鎖帶一個有效期限，持有者必須定期續約（也就是心跳／heartbeat）。持有者一消失就不再續約，期限一到租約自動失效，別人就能接手。

例 
持有者：每 10 秒更新一次 heartbeat = now()
接手者：檢查 (enabled AND heartbeat > now() - 60 秒)
        → 條件不成立就表示對方已消失，我可以接手

期限的選擇是一個取捨：太短會在對方只是暫時卡住時誤判、造成兩邊同時執行；太長會讓故障後的空窗期變長。所以租約一定要搭配上一個觀念的原子操作——因為誤判是設計中允許發生的事。

還有一個必須明確決定的問題：查不到那筆狀態紀錄時，該算「有人在跑」還是「沒人在跑」？這決定了機制壞掉時系統偏向哪一邊，必須由後果決定——漏做的代價大就偏向照做，重複做的代價大就偏向不做。沒有明確宣告的話，它會壞向實作細節碰巧決定的那一邊。

所以任何「誰在負責」的協調機制都要有期限與心跳，不要用永久鎖。並且要明確寫下「狀態讀不到時算什麼」。

5排程表達式不帶時區

經典的排程語法有五個欄位：分、時、日、月、星期。* 是每一個，*/5 是每五個，逗號列舉，連字號表範圍。

例 
*/5  9-13  *  *  1-5     每週一到五、9 到 13 點、每 5 分鐘
30   10     *  *  *       每天 10:30
45   10,23  *  *  *       每天 10:45 和 23:45

┌─ 分 (0-59)
│ ┌─ 時 (0-23)
│ │ ┌─ 日 (1-31)
│ │ │ ┌─ 月 (1-12)
│ │ │ │ ┌─ 星期 (0-6，0 是週日)
* * * * *

重點是這串表達式裡沒有時區的位置。時區來自執行它的那個排程器的設定，而排程器的預設時區經常不是你所在的時區。

後果是最典型的安靜出錯：任務每天都準時執行，只是準時在別的地方的下午。所有「它有沒有跑」的檢查都會顯示正常，只有去對紀錄的時戳才會發現。

所以每一個排程都要明確宣告時區，不要依賴預設值。而如果你的平台只吃固定時區（通常是 UTC），就自己換算好並在旁邊註明——45 10 * * * 要寫上「＝台北 18:45」，否則半年後沒人看得懂那個 10 是什麼。

另外一個坑：有日光節約時間的地區，本地時間一年會有一天缺一小時、有一天多一小時。排在那個區間的任務會少跑或跑兩次。系統內部一律用 UTC 儲存與計算、只在顯示時轉成本地時間，可以避開這一整類問題。

6「至少一次」是現實，所以消費端必須幂等

任何跨網路的訊息傳遞都面對同一個難題：送出去之後沒收到確認，你不知道對方到底收到了沒有。於是只有兩種選擇：重送（可能重複）或不重送（可能遺失）。

例
語意代價
at-most-once 最多一次可能遺失
at-least-once 至少一次可能重複
exactly-once 剛好一次在分散式環境下無法單靠傳遞機制達成

所以實務上的答案固定是：用「至少一次」的傳遞，加上一個幂等的接收端。重複到達沒關係，因為接收端處理第二次時什麼都不會多做。

幂等接收端的實作就是唯一鍵：把「這件事的身分」定義清楚，寫進唯一約束。而身分的定義要包含所有「會讓它變成一件新事」的參數——少一個，改了設定後重新發生的事件會被誤判成重複而丟掉。

所以不要追求「保證只送一次」，那是做不到的。要做的是讓「收到兩次」變成無害。任何處理外部訊息、任何會被重跑的任務，都要先回答「重複執行會怎樣」。

L7

部署與拓撲

你的程式實際跑在哪裡，以及它和其他東西之間的線怎麼接。

為什麼學

不懂這一層，你會做出兩類錯誤判斷：把「距離造成的慢」誤判成程式效能問題，然後去優化一個部署後根本不存在的瓶頸；以及不知道自己的哪一條線暴露在公開網路上。

好消息是這一層的門檻很低——能畫出一張標註清楚的圖，就守住大半。

要學什麼

  • 容器是什麼——隔離的程序，不是虛擬機 namespace, cgroup
  • 距離的算術——往返時間乘以次數 round-trip time, chatty app
  • 服務怎麼被找到——內部名稱與對外入口 service discovery, ingress
  • 組態從外面注入——同一份產物跑在不同環境 config injection

核心觀念

1容器是被隔離的程序，不是一台小電腦

容器（container）常被想成「輕量虛擬機」，這個比喻會誤導。它其實就是一個普通程序，只是作業系統對它撒了兩個謊：

命名空間（namespace）讓它只看得到屬於自己的東西——自己的檔案系統視角、自己的程序清單、自己的一組網路介面。資源限制（cgroup）限制它能用多少記憶體與處理器。沒有第二個作業系統核心，也沒有開機過程。

例

「自己的一組網路介面」這件事直接解釋了一個常見困惑：容器有自己的迴環位址。所以容器裡綁 127.0.0.1 的意思是「只有這個容器內部連得到」，就算端口映射設對了也一樣連不進去。

資源限制也解釋了另一件事：容器被記憶體上限殺掉時，是外面的機制送出強制終止訊號，程式來不及留下任何訊息。你只會看到結束碼 137。

所以容器裡一律綁 0.0.0.0；看到結束碼 137 先去看記憶體上限，不要在程式碼裡找原因。

2距離的算術：往返時間乘以次數

每一次查詢都要等資料在網路上跑一趟來回，這叫往返時間（round-trip time）。同一個機房內部大約 1 毫秒，跨大陸大約 200 到 300 毫秒——差兩個數量級。

關鍵是它會被查詢次數放大。一個頁面下十幾條查詢是很平常的事：

例
路徑單次往返× 12 次查詢
同機房內網1 ms12 ms
跨公網250 ms3,000 ms

同一份程式碼、同一個資料庫、同樣的查詢，差別只有距離，結果是「感覺很快」和「每次載入等三秒」。

所以「本機連雲端資料庫」的開發體驗天生就慢，那個慢是預期行為，不是效能問題。拿它當效能指標會得到完全錯誤的結論。

解法有兩個方向：把距離縮短（把服務部署到資料庫旁邊）或把次數減少（合併查詢）。前者通常便宜得多。

所以看到「每一次都慢」而不是「某一次慢」，先算距離乘次數，再考慮優化程式。

3服務怎麼被找到：內部名稱與對外入口

雲端上的服務沒有固定位址——它可能被重啟、被搬到另一台機器、同時跑三份。所以平台提供兩套定位機制，而它們的安全性質完全不同：

例
機制怎麼運作誰連得到
內部名稱平台的內部網域名，指向當前實際位置只有同一個網路邊界內的服務
對外入口在邊緣開一個公開端口，轉發到內部服務全世界

「同一個專案／同一個網路」在雲端不是組織上的分類，它是一條網路邊界。邊界之內走內網（快、不對外暴露），之外的一切都要繞公網。

另外，你的服務要監聽的端口通常是平台指定並用環境變數注入的，不是你決定的。把端口寫死在某些平台會直接啟動失敗。

所以每開一個對外入口，就是多開一道全世界都能敲的門。沒有流量在用的入口要關掉——臨時需要時用平台的臨時通道，用完即斷，這樣它平時在公網上是不存在的。

4組態從外面注入，產物保持乾淨

同一份程式要跑在本機、測試、正式三個環境，而三個環境的資料庫位址、金鑰、網域都不同。原則是：把這些差異全部放進環境變數，讓程式產物本身完全不含環境資訊。

這樣同一份產物可以原封不動地部署到任何環境，而「換環境」不需要重建。反過來，把設定寫進程式或打包進映像檔，就等於每個環境要一份不同的產物，而它們會慢慢分岔。

例

平台通常支援引用式變數——一個服務的變數可以指向另一個服務的值：

DATABASE_URL = postgresql://user:${{Postgres.PASSWORD}}@${{Postgres.HOST}}:5432/mydb

好處不是省打字，是輪替密碼時只需要改一個地方。複製貼上的做法在輪替時一定會漏掉一處，而漏掉的那一處會在幾天後以「某個服務連不上」的形式出現。

所以任何會隨環境變化的值都走環境變數，能用引用式就不要複製貼上。而部署時如果是直接上傳目錄，一定要有排除清單——否則本機的秘密檔案與虛擬環境會一起上去。

L8

身分、秘密與權限

誰碰得到你的東西，以及秘密放在哪裡。

為什麼學

這一層的知識量不大，但錯誤的代價最高，而且最常見的錯法是誤以為自己已經做好了——接了第三方登入就以為權限管好了，開了加密就以為安全了。

更麻煩的是它的失敗特別安靜：授權設錯時，登入流程一切正常、日誌上每一次登入都是成功且合法的，只是不該進來的人進來了。

要學什麼

  • 認證與授權的分別——你是誰 vs 你能做什麼 authentication vs authorization
  • 授權碼流程——第三方登入實際怎麼走 OAuth 2.0, OIDC, PKCE
  • 權杖的性質——簽章不是加密 JWT, signing
  • 加密做什麼、不做什麼——傳輸與身分 TLS, mTLS
  • 秘密的存放與輪替——換一把金鑰是一個動作 secret management, rotation

核心觀念

1認證與授權是兩件事，而第三方只解決前者

認證（authentication）回答「你是誰」，像查驗護照。授權（authorization）回答「你能做什麼」，像簽證——護照真實，不代表你能入境。

接上第三方登入時，你把認證委外了：對方負責確認這個人是誰。但授權仍然完全是你的責任。如果你沒有另外設定允許清單或角色，那麼全世界任何持有該平台帳號的人都能進來——而且認證層完全正常，日誌上每一次登入都合法。

例

同樣是「忘記設一個值」，方向完全相反：

忘記設定後果音量
允許的帳號清單授權層失效、認證層正常 → 任何人都進得來安靜
用戶端憑證登入流程無法建立 → 所有人被擋在外面大聲，而且在保護資料

所以每一個設定值都要知道自己屬於哪一種。理想的設計是讓所有安全相關的缺失都壞向「擋住」——沒有憑證就不提供服務，而不是沒有憑證就不檢查。

所以接完第三方登入之後，還有一半的工作沒做。而在設定齊全之前，系統應該是擋住所有人，不是放行所有人。

2授權碼流程：把「用第三方登入」走一遍

「用某個平台的帳號登入」背後是一套標準流程。它看起來繞，但每一步都在解決一個具體問題。四個角色先認清：使用者、你的應用、認證伺服器（那個平台）、資源伺服器（要被存取的 API）。

例 
1. 使用者點「用 X 登入」
2. 你把他重導到 X，網址帶上：
     client_id      你的應用身分（公開的）
     redirect_uri   完成後要回到哪裡
     scope          你要求的權限範圍
     state          一段隨機字串
     code_challenge 一段雜湊值
3. 使用者在 X 上登入、同意授權
4. X 把他重導回你的 redirect_uri，帶回一個 code 和原本的 state
5. 你檢查 state 是不是自己發出去的那一個
6. 你的後端拿 code + client_secret + code_verifier 去跟 X 換 token
7. 拿到 token，才能代表使用者做事

三個容易被當成裝飾的參數，各擋一種攻擊：

參數擋什麼
state別人偽造一個登入回呼塞給你的使用者（CSRF）。你只接受自己發出過的那個值。
redirect_uri授權碼被送到攻擊者的網站。所以它必須事先在平台註冊，且完全比對——這也是為什麼三處位址必須一字不差。
PKCE授權碼在重導過程中被攔截。你先送出一段雜湊值，換 token 時才送出原文；攔到 code 的人沒有原文，換不到 token。

另外釐清兩個常被混用的名字：OAuth 2.0 本來只管「授權」（讓你的應用代表使用者存取資料）；OIDC 是疊在它上面的一層，才真正回答「這個人是誰」，多給你一個含身分資訊的權杖。做登入用的是後者。

所以這個流程的每一步都不能省。而它是典型的多步驟流程——登入頁渲染正常完全不代表流程走得完，必須實際點到底才算驗證過。

3權杖：任何人都讀得懂，只有持金鑰的人能簽

常見的權杖格式（JWT）長成三段，用點分開：標頭．內容．簽章。前兩段只是把 JSON 做了 Base64 編碼——Base64 是編碼，不是加密。任何拿到權杖的人都能直接讀出裡面的內容。

簽章的作用不是隱藏，是證明沒有被改過。伺服器用秘密金鑰簽，驗證時重算一次；內容被動過一個字，簽章就對不上。

例 
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiJ1MSIsImFkbWluIjpmYWxzZX0 . 4Rt2_kQ...
└─── 標頭 ───────────┘ └─── 內容 ─────────────────────┘ └─ 簽章 ─┘

# 中間那段解出來就是明文：
{"sub": "u1", "admin": false}

兩個直接推論：

不要把秘密放進權杖內容。使用者自己看得到，也可以貼給任何人看。

簽章金鑰洩漏等於任何人都能偽造任何身分。他可以自己簽一個「我是管理員」的權杖，而伺服器驗證會通過。這件事最可怕的地方是沒有任何跡象——沒有失敗的登入、沒有異常錯誤，每一次存取在系統眼中都完全合法。

所以簽章金鑰要當成最高等級的秘密，並且定期輪替。這一類風險無法靠偵測發現，只能靠預防。

4加密做什麼、不做什麼

傳輸加密（TLS，也就是網址上的 https）做兩件事：把內容加密，讓路上的人看不到；以及驗證伺服器的身分，靠憑證確認你連到的真的是那個網域。

它不做的事同樣重要：它不驗證客戶端是誰（任何人都能發起一個加密連線），也不阻止任何人來敲門。

例

所以一個對外開放的資料庫端口，即使全程加密，唯一的防線仍然是那組密碼：

加密保證的：路上的人看不到你的密碼與資料
加密不保證的：全世界都可以連到這個端口、不斷嘗試登入

如果要連「客戶端是誰」也驗證，需要雙向驗證（mTLS）——客戶端也要出示憑證。但更實際的做法通常是：先不要讓它暴露在公開網路上。

所以「已經加密了」不能當成安全結論。要分開問三件事：路上會不會被看到、對方是不是真的它、誰能連進來。

5秘密的存放位置，以及「能輪替」這個要求

秘密有幾個合理的存放位置，各有各的角色。挑錯位置的代價是洩漏：

例
位置放什麼進版控嗎
.env本機開發用的實際金鑰不進
.env.example只有欄位名稱與取得方式的說明要進（讓別人知道要填什麼）
平台服務變數正式環境的金鑰不進（由平台注入）
工具自己的憑證管理該工具要用的金鑰不進

最後一項有個延伸：有些工具會刻意封鎖「從表達式讀環境變數」，因為那條路徑很容易讓秘密出現在日誌或匯出檔裡。這種限制要順著走，不要想辦法繞過。

還有一個常被忽略的要求：換一把金鑰必須是一個動作，不是一場考古。如果同一個值被複製到五個地方，輪替時你一定會漏掉一處，而漏掉的那一處會在幾天後以「某個東西突然連不上」的形式出現。這是引用式變數真正的價值。

所以盤點秘密時，每一個都要能回答四件事：存在哪／誰能讀／洩漏了會發生什麼／怎麼輪替。第四欄答不出來的最多，而它代表：那把金鑰真的洩漏時，你沒有辦法應對。

L9

觀測與除錯

怎麼知道它壞了，以及壞了之後怎麼定位。

為什麼學

前面八層的錯誤能不能被你看見，由這一層決定。沒有它，你的系統可能已經壞了兩個月而你不知道——因為畫面一切正常。

而它有一個特別的盲區：「什麼都沒發生」不會產生任何紀錄，也不會觸發任何告警。所以需要一個專門用來發現「沒發生」的機制，而這個機制最常被漏掉。

要學什麼

  • 三根柱子——日誌、指標、追蹤各回答什麼 logs, metrics, traces
  • 結構化日誌——可查詢的紀錄 structured logging
  • 「沒發生」的盲區——死人開關 dead man's switch, freshness
  • 告警設計——去重與疲勞 alert fatigue, deduplication
  • 讀堆疊與二分定位——找交界 stack trace, bisection

核心觀念

1三根柱子：各自回答不同的問題

觀測（observability）的常見分法是三種資料，它們不能互相取代，因為回答的問題不同：

例
柱子是什麼回答
日誌
logs		一件一件的事件紀錄「那一次到底發生了什麼」
指標
metrics		隨時間變化的數字「現在正常嗎、趨勢在變壞嗎」
追蹤
traces		一個請求走過的所有環節「這三秒花在哪一段」

小系統不需要第三根（它是為了多服務串接而生的）。但前兩根都要有：只有日誌，你無法回答「這個月比上個月糟嗎」；只有指標，出事時你不知道那一次的細節。

最有價值的起點是單一健康指標：一個地方、一句查詢，回答「系統現在好不好」。沒有它，你只能靠感覺，而感覺會被「畫面正常」騙過去。

所以先做兩件事：一張記錄每次執行結果的表，以及一句能判斷整體健康的查詢。這兩樣的成本很低，但它們是其他一切的基礎。

2日誌要能被查詢，所以要有結構

「跑過了」這種日誌等於沒有日誌，因為影響 0 筆和影響 3000 筆都會顯示「跑過了」。一筆有用的執行紀錄要包含四件事：做了什麼、成功或失敗、影響幾筆、訊息是什麼。

而寫法要有結構（structured logging）——用固定的鍵值而不是自由文字。因為只有結構化的日誌可以被篩選、統計、比較。

例 
# 沒有結構：只能用眼睛看
更新完成，共 1 筆有問題

# 有結構：可以查詢
{"job":"daily_update","status":"FAIL","rows":248,"symbol":"2330",
 "msg":"quote empty","ts":"2026-09-09T18:30:12+08:00"}

# 於是這些問題都能回答：
#   這個月失敗過幾次？
#   哪一個標的最常出問題？
#   平均處理筆數是不是在下降？

時間戳一定要帶時區。少了時區的時間戳在跨系統比對時會產生幾小時的偏移，而那種偏移很難被發現。

所以把執行紀錄設計成一張可以查詢的表，而不是一堆文字。這是低成本、高回報的一步——之後所有「這是什麼時候開始的」的問題，都靠它回答。

3「什麼都沒發生」是盲區，需要死人開關

日誌與告警有一個共同的前提：要有事情發生，它們才會產出東西。於是「任務完全沒有執行」這個狀況，兩者都看不到——沒有錯誤日誌，因為沒有錯誤；沒有告警，因為沒有觸發條件。

發現「沒發生」只有一種辦法：主動去問「最新的東西是什麼時候的」。這種機制叫死人開關（dead man's switch）——不是等壞消息來，而是「太久沒聽到好消息就當成壞消息」。

例 
-- 資料新鮮度檢查：落後超過容忍天數就是異常
SELECT symbol, MAX(date) AS latest,
       CURRENT_DATE - MAX(date) AS days_behind
FROM daily_prices
GROUP BY symbol
HAVING CURRENT_DATE - MAX(date) > 4;      -- 4 天，涵蓋週末與連假

那個閾值是這個機制的重點。設成 1 天，每個週末都會誤報；而規律誤報的下場是被忽略，等於這條防線消失了，只留下一個讓你安心的假象。

閾值要按真實世界的節奏設，不是按直覺設。有週末的資料就要涵蓋週末，有連假的要涵蓋連假。

所以每一個週期任務都要配一句新鮮度查詢，而且閾值要用真實節奏推算。這是唯一能發現靜默停擺的手段。

4告警設計：對症狀告警，並且去重

兩個原則。第一，對症狀告警，不對原因告警：「資料超過四天沒更新」是症狀，「某個 API 回 500」是原因。原因有無限多種，症狀只有幾種；對症狀告警才不會漏掉你沒想到的原因。

第二，告警疲勞是一種失效模式，不是使用體驗問題。同一件事重複轟炸會讓人關掉通知，而那比沒有告警更糟——因為你以為自己有在被提醒。

例

所以告警要去重，而去重鍵的設計是關鍵：它要包含所有「會讓這件事變成一件新事」的參數。

去重鍵 = (標的, 日期, 級別, 門檻參數)

# 少了「門檻參數」會發生什麼：
#   你把門檻從 10% 調成 5%
#   價格跌破新的那條線（這是新資訊，該通知）
#   但系統認為「今天這個標的這個級別已經發過了」→ 抑制掉
#   你收不到通知，而且以為系統在看著

兩個方向的錯都要想到：太鬆會變成每五分鐘轟炸同一件事，一天幾十次；太緊會讓真正的新事件被誤判成重複。

所以設計告警時把去重鍵明確寫下來，並逐項確認「這個參數改變了，還算同一件事嗎」。答案是「不算」的參數，就必須在鍵裡面。

5讀堆疊：找你的程式與函式庫的交界

錯誤堆疊（stack trace）是「出錯時，函式呼叫的層層路徑」。讀它有個前提要先搞清楚——不同語言的排列方向相反：

例
語言最內層（出錯處）在
Python最後一行（開頭那句 most recent call last 就是在講這件事）
Java / JavaScript最上面一行

真正的技巧是：找「你的程式」與「別人的程式」的交界。根因常常不在任何一層裡面，而在兩個函式庫的交界處——各自都按自己的規則正常運作，但兩者的假設互相衝突。你的那一行只是碰巧觸發了它。

java.lang.IllegalArgumentException: Can only use lower 16 bits for requestCode
  at androidx.fragment.app.FragmentActivity.checkForValidRequestCode(...)   ← 函式庫 A：只接受 16 位元
  at androidx.activity.ComponentActivity$...onLaunch(...)                   ← 函式庫 B：產生 32 位元
  at com.example.ui.MainScreenKt.MainScreen(MainScreen.kt:463)              ← 你的程式：只是呼叫了它

根因在 A 與 B 的交界，不在你那一行。盯著自己的程式看不出問題。

所以讀堆疊時先標出「哪幾行是我的」，再看緊鄰它的上下兩層。而最貴的反模式是「掩蓋」——為了讓它看起來能跑而包住那個錯誤。錯誤不會消失，只是失去了聲音，而那個聲音是你唯一免費得到的資訊。

6二分定位：不要從頭讀程式碼

當你不知道問題在哪，最有效率的方法不是逐行閱讀，而是二分（bisection）：把路徑切一半，確認中點是對的還是錯的，然後只往有問題的那一半找。每一次切半，範圍就少一半。

例

二分可以用在兩個維度上：

維度做法
資料路徑從來源到畫面之間找中點（例如資料庫裡那筆值），確認在中點時資料是對的還是錯的 → 問題在中點之前或之後
時間軸「上個月還好的」→ 在版控歷史裡二分，找出哪一次改動開始出錯（git bisect 就是做這件事的工具）

還有一個讓定位變便宜的準備工作：把外部世界的各種樣貌存成固定樣本，讓邏輯可以離線重播（golden files / replay fixtures）。有了它，你可以在任何時候重現任何一種狀況，不必等它再發生一次。

所以遇到不明問題，先問「路徑的中點在哪、我怎麼看那個中點」。這比讀程式碼快一個數量級。而除錯記錄要以症狀開頭而不是原因——因為下次你遇到的是症狀。

動手方向
關掉某一個週期任務，然後只靠現有的觀測手段，看你多久之後會發現。如果答案是「永遠不會」，缺的就是新鮮度查詢；如果答案是「下次剛好去看的時候」，那也等於永遠不會。在還有人依賴的系統上先確認停一段時間不會造成不可逆的資料缺口。

關於這份講義的邊界

它不教程式語言、語法與演算法。那是另一層的事，而且那一層錯了會立刻報錯——你會知道，也查得到。這份講義收的是另一種知識：不懂的時候不會報錯，只會安靜地產生錯的結果。

它也不教語法細節——觸發器怎麼寫、排程表達式的每一種變體、遞迴查詢怎麼組。這一層需要的是「該不該用它」的判斷，而那個判斷不需要語法。真的要寫的時候再查，或交給工具。

兩個目前刻意排除、但條件變了就該補的題目。前端視覺與樣式：這類故障幾乎都是大聲失敗（畫面看得出來），也不影響資料正確性——但如果你的工作需要親自判斷介面設計，就該補。效能調校與索引優化：小規模系統碰不到那個門檻——但當資料量或使用者數成長到查詢開始變慢，就該補。

讀完一層之後最有效的一步，是把那一層的「動手方向」真的做一次。這一層的知識有個特性：讀過會懂，但只有親手看過它壞掉一次才會變成直覺。
